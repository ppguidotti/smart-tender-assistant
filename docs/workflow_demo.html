Dal bando alla decisione: il workflow operativo di estrazione dei requisiti

Una pipeline a due stadi che legge i documenti di una gara pubblica, ne estrae i requisiti in modo strutturato e tracciabile, e li porta nella dashboard di analisi. Ore di lettura manuale → minuti.

Caricamento documenti UI · Repository

L'utente trascina i documenti di gara nella dashboard e avvia l'analisi con un click. Nessuna preparazione manuale del file.
Input
Capitolato Gara - Anonimizzato.pdf   (7 pagine)
Requisiti_Anonimizzato.pdf           (4 pagine)
Azione
▶ Carica e analizza  →  avvia pipeline B1+B2
1

B1 — Document ingestor Apache Tika

Tika fa da router universale dei formati (1400+ tipi): rileva il MIME dal contenuto, estrae testo e metadati e produce un ParsedDocument uniforme. I blocchi a valle non sanno né devono sapere se l'origine era un PDF, un DOCX o una email.
Input
file binario (qualsiasi formato)
Output · ParsedDocument
{
  "document_id": "…",  // uuid deterministico (sha256)
  "source": {
    "mime_type": "application/pdf",
    "pages": 7,
    "hash_sha256": "…"
  },
  "raw_text": "…Capitolato Speciale d'Appalto…"
}
2

B2 · stadio 1 — Estrazione LLM Grok 4.1 · JSON-mode

Il testo di ogni documento viene passato a un LLM con un prompt specializzato e uno schema JSON vincolante (temperatura 0). L'LLM si concentra solo sulla semantica: identifica i requisiti, li rende atomici, ne stima la confidenza e cita il passaggio testuale di origine.
Input
raw_text + prompt "estrazione requisiti"
response_format = json_schema (vincolante)
Output · requisito grezzo
{
  "categoria": "idoneita_professionale",
  "descrizione": "Iscrizione MePA categoria
                   Informatica…",
  "obbligatorio": true,
  "fonte_testuale": "…iscritti al MePA…",
  "confidenza": "alta"
}
3

B2 · stadio 2 — Merge & deduplica embeddings · cosine

Lo stesso requisito può comparire in più documenti con formulazioni diverse. Gli embedding multilingue (e5) misurano la similarità semantica; i requisiti vicini vengono raggruppati (componenti connesse) e fusi, conservando la formulazione più completa e l'unione delle fonti.
Input
requisiti grezzi di tutti i documenti
soglia similarità = 0.93
Output
requisiti deduplicati
+ documenti[]  (unione fonti)
+ fonti_testuali[]
4

B2 · mapping — Normalizzazione al contratto Pydantic v2

Ogni requisito viene mappato sul contratto applicativo: tassonomia QUALIFICAZIONE / NORMATIVA / TECNICA / AMMINISTRATIVA, tipo ESCLUDENTE / PREFERENZIALE, confidenza in [0,1] e — soprattutto — una SourceLocation che riporta documento e offset del testo originale.
QUALIFICAZIONE ESCLUDENTE REQ-001
Iscrizione al MePA — categoria “Informatica, Elettronica, Telecomunicazioni”.
📍 Fonte: Capitolato Gara · pag. 1
SourceLocation → document="Capitolato Gara.pdf", char_start=0, char_end=37
Confidenza estrazione 0.95
Il differenziatore → ogni requisito porta con sé la prova della sua origine. In dashboard, dalla scheda del requisito si risale al punto esatto del documento.
5

Output — Dashboard di analisi Streamlit

I requisiti normalizzati alimentano la dashboard: raggruppati per categoria, con badge di tipo e citazione della fonte. Da qui partono i blocchi successivi — gap analysis contro il profilo aziendale e decisione GO / NO-GO.
Output · ExtractionResult
{
  "requirements": [ 8 requisiti ],
  "extraction_summary": {
    "by_category": {…},
    "avg_confidence": 0.95
  },
  "needs_review": []
}
